## 3. New findings

**R2-1 · high · migration/startup · `core/database.py:338-352` + `:174-177` (init order `:61-63`); `models/database.py:313-330` (unguarded at `:280`)** — measured.
Deterministic backfill collides on pre-P1 rows that share a tuple. Pre-P1 the legacy store was a plain INSERT (base `core/database.py:580-585`) and the ORM deduped on `name` only (base `models/database.py:387`), so `POST /api/credentials` with `admin-pw1` and `admin-pw2` for `admin@CORP` wrote two rows into each store. Probe A: such a legacy DB → `Database(path)` raises `sqlite3.IntegrityError: UNIQUE constraint failed: credentials.account_ref` (UPDATEs commit identical refs, then `_create_tables` builds the unique index) → Framework/CLI cannot start, and every restart repeats it. Probe B: the matching ORM DB → `_migrate_credentials_schema` raises the same error inside `DatabaseManager.__init__` (transaction rolled back, rows stay un-migrated, fails on every start) → API server and dashboard cannot construct `db_manager`. Round B's `uuid4` could not collide, so this is new to this round. Fix: neither migration may raise. Before creating the index, group rows by `(username, scope, domain, local_host)`; keep the lowest rowid as the account and either fold the extra rows away (delete after logging, optionally stashing their password/hash in `metadata`) or give extras a deterministic per-row fallback ref (uuid5 over tuple + rowid). Prefer the fold: with fallback refs the startup sync (`framework.py:167` → ref miss → tuple match → overwrite) silently collapses the ORM copy anyway. Add a regression test with duplicate-tuple pre-P1 rows in each store. The merge policy is an owner call; the no-raise requirement is not.

**R2-2 · high (suite not green; product behavior correct) · `api/server.py:418-420` vs `tests/unit/api/test_server.py:199-207, 220-227, 686-697`** — measured.
The name fallback calls `.filter(...).limit(2).all()`; the three pre-existing not-found tests mock only `query().filter().first()` → `None`, so the fallback receives a `MagicMock` (len 0, truthy), returns `matches[0]`, and `credential_response` raises a pydantic `ValidationError` → 500 instead of 404. With a real session all three routes return 404 (probed). The implementer could not run this module. Fix: in the three tests add `mock_session.query.return_value.filter.return_value.limit.return_value.all.return_value = []` (test-only); or make `_resolve_credential` tolerate the mock shape by using `.first()` plus a `.count()` check.

**Not raised, for the record:** rejecting a second password candidate for the same account via the API (now 400, pre-P1 accepted under a different name) is the intended consequence of the R-1/R-4 ruling; its only defect is the migration path in R2-1. A legacy row with NULL `metadata` crashes `get_credentials` (`json.loads(None)`), but that is pre-existing and not reachable from any writer.
